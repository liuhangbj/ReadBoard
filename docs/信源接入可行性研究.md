# Readboard 新信源接入可行性研究

> 调研日期：2026-07-30
> **修订：2026-07-31 — 抖音结论由「不可行」修正为「可行（浏览器引擎方案）」，详见 §三**
> 调研对象：知识星球、哔哩哔哩、抖音、小红书
> 方法：本地实测探针（真实 HTTP 请求 + 真实浏览器引擎）+ 现有能力资产盘点 + Readboard 源码核对

---

## 一、结论摘要

Readboard 需要的是**订阅式信源**——能被周期性拉取、返回增量列表、带稳定游标的入口。**这是本次评估的唯一轴心**：能抓单条 URL ≠ 能作为信息源。

| 平台 | 可行性 | 订阅式入口 | 认证门槛 | 签名破解方式 | 建议 |
|------|--------|-----------|---------|---------|------|
| **哔哩哔哩** | **高度可行** ★首选 | ✅ 动态 / 收藏夹 / 合集 | 部分入口**零认证** | WBI 纯 MD5，代码直接复现 | **下一个实现** |
| **抖音** | **可行** ★（修订） | ✅ 用户投稿列表 | **零登录零 Cookie** | **不逆向**：浏览器引擎内执行 | 值得排期 |
| **知识星球** | 可行 | ✅ groups / topics | token（1–3 月有效） | 无（token-only） | 挂待办，方案已就绪 |
| **小红书** | 技术可行（修订） | ✅ user_posted | **需登录态**，内置扫码可解 | **不逆向**：`window._webmsxyw` | 可选高级功能，风险自担 |

**分水岭不是"��名能否逆向"，而是"能否让平台自己的 JS 生成签名"。** 初版评估的方法论缺陷在于：全程用 curl / Python 裸 HTTP 测试，隐含假设了"无浏览器环境"。而 Readboard 是原生 macOS 应用，`Sources/ReadBoard/ContentView.swift:2` 与 `Design/Styles.swift:5` 已 `import WebKit`——**完整的浏览器引擎本就在依赖里**。

于是问题从「能否在 Swift 里静态复现 a_bogus 混淆虚拟机」（不可行）变成「能否在 WebView 里让抖音自己的 JS 算出签名」（已实测可行）。这两个问题的难度差了一个数量级。

**四个平台按「卡在哪一层」重新归类，比按「难度」归类��有解释力：**

| 卡点层 | 平台 | 破解方式 | 剩余成本 |
|--------|------|---------|---------|
| 无卡点 | B站（收藏夹） | 裸 HTTP 直通 | 无 |
| 签名层 | B站（动态流） | WBI 纯算法复现 | 低 |
| 签名层 | 抖音 | 浏览器引擎执行平台 JS | 中（需 WebView 基建） |
| **鉴权层** | **小红书** | **内置扫码登录取得 web_session** | **技术低，账号风险高** |
| 鉴权层 | 知识星球 | 用户手工填 token | 低 |

小红书是唯一卡在鉴权层、且需要用户**主账号**的平台——这决定了它的成本不在工程，在风险。

## 二、哔哩哔哩 — 高度可行（推荐优先实现）

### 2.1 实测结果

全部为本机真实请求，非文档推断。

| 接口 | 用途 | 签名 | Cookie | 实测结果 |
|------|------|------|--------|---------|
| `/x/polymer/web-dynamic/v1/feed/space?host_mid=` | **UP 主动态流** | WBI | buvid3 | ✅ `code=0`，12 条，`has_more=true` |
| `/x/v3/fav/resource/list?media_id=` | **收藏夹内容** | 无 | 无 | ✅ `code=0`，**裸请求直通** |
| `/x/web-interface/view?bvid=` | 视频详情 | 无 | 无 | ✅ `code=0` |
| `/x/web-interface/card?mid=` | UP 主信息 | 无 | 无 | ✅ `code=0` |
| `/x/frontend/finger/spi` | 取 buvid3/buvid4 指纹 | 无 | 无 | ✅ `code=0` |
| `/x/player/wbi/v2?aid=&cid=` | 视频字幕轨 | WBI | buvid3 | ✅ `code=0`（AI 字幕需登录态） |
| `/x/space/wbi/arc/search?mid=` | UP 主投稿列表 | WBI | buvid3 | ❌ `HTTP 412`（风控更严） |

**UP 主动态流返回样例（影视飓风 mid=946974）**：
```
1230704367404843008 | DYNAMIC_TYPE_DRAW  | (图文动态)
1230410303839142040 | DYNAMIC_TYPE_AV    | 动态视频｜只看开场，你能猜到这条视频多少播放吗？
```

`arc/search` 的 412 不构成阻碍——动态流已完整覆盖 UP 主的视频投稿、专栏和图文，且信息更丰富。

### 2.2 WBI 签名机制（已验证可复现）

纯算法，无 JS 依赖，Swift 可用 CryptoKit 直接实现：

```
1. GET /x/web-interface/nav  → 取 wbi_img.img_url / sub_url
   （即便 code=-101 未登录，wbi_img 字段照常返回）
2. img_key = 文件名去扩展名，sub_key 同理
3. mixin_key = (img_key + sub_key) 按 64 位固定重排表取前 32 字符
4. 请求参数 + wts(时间戳) 按 key 字典序排序并 urlencode
5. w_rid = MD5(排序后的 query + mixin_key)
```

实测算出的 mixin_key：`ea1db124af3c7062474693fa704f4ff8`，签名通过。

**风控前置条件**：必须先调 `/x/frontend/finger/spi` 取 `buvid3`/`buvid4` 并作为 Cookie 携带，否则 WBI 签名正确也会被 412 拦截。这一步是公开接口，无需登录。

### 2.3 建议的三类信源入口

1. **UP 主动态**（`identifier = mid`）— 最贴合"订阅一个创作者"的心智，覆盖视频+专栏+图文
2. **收藏夹**（`identifier = media_id`）— **零认证零签名**，用户在 B站 App 收藏即入库，工程量最小，建议作为 Phase 1 的最小可用版本
3. **视频合集/系列**（`identifier = season_id`）— 追更系列内容

### 2.4 与 Readboard 现有管线的衔接

- **视频类** → `meta.audio_url` 写入音频流地址，直接复用现有 `TranscribePipeline`。仅需在 `SourceStore.swift:82` 的 `transcribable` 判断中加入 `|| stype == "bilibili"`。
- **专栏 / 图文动态** → 正文在动态接口中已直接返回，可置 `fetch_status=2` 并写 `content_md`，跳过 `FullTextFetcher`。
- **去重与增量** → `guid` 用 `dynamic_id`（动态）或 `bvid`（收藏夹）；增量游标用动态接口返回的 `offset` / 收藏夹的 `pn`。
- **字幕优先于转写** → 若 `player/wbi/v2` 返回字幕轨，直接取字幕作正文，可省下 Whisper 转写开销。此路径需登录 Cookie，建议作为可选增强项。

### 2.5 风险

| 风险 | 等级 | 缓解 |
|------|------|------|
| WBI mixin_key 重排表变更 | 低 | 该表多年未变；可做成配置项 |
| 风控加严（412 扩散到动态接口） | 中 | 已预留收藏夹这一零认证降级路径 |
| 请求频率限制 | 低 | 随机延迟 + 单源单次 ≤2 请求 |
| 合规 | 低 | 公开内容、个人自用、非商用；不绕过付费墙 |

## 三、抖音 — 可行（修订结论）

> **本节为 2026-07-31 修订。** 初版结论「订阅式不可行」是**方法论错误导致的误判**，非事实错误——所测路径确实全部封死，但漏测了最关键的一条：浏览器引擎内执行。触发复查的外部证据是「得到大脑」（Get 笔记）已上线「订阅抖音博主 + 每日 8 点自动更新」功能，证明账号级增量同步在工程上成立。

### 3.1 决定性实测

在真实浏览器引擎（Playwright + Chromium）中打开博主主页，随后**在页面上下文内调用抖音自己的接口**：

```
页面内 fetch aweme/v1/web/aweme/post/
→ HTTP 200, 785,572 字节
→ status_code=0, aweme_list=16 条, has_more=1
→ max_cursor=1727113929000（分页游标）
```

**全程未登录、无人工 Cookie、无 a_bogus 逆向。** 浏览器加载页面时抖音自己的 JS 已完成环境初始化与签名注入，页面内发起的请求天然携带合法签名。

对照同一时刻的裸 HTTP 请求（相同 URL、相同 UA、相同 Referer）：`HTTP 200, size=0`。**同一个接口，浏览器内通、浏览器外不通**——这就是全部差异所在。

**取得的字段（实测样例）**：

| 字段 | 实测值 |
|---|---|
| aweme_id | `7560722398758112563` |
| desc（正文） | `30秒带你欣赏沈星回有多帅#沈星回 #恋与深空` |
| create_time | `1760367866` → 2025-10-13 |
| video.duration | `5549` ms |
| play_addr | `https://v26-web.douyinvod.com/...` 无水印直链 |
| cover | 封面图 URL |
| images[] | 图集（图文笔记） |
| statistics | `digg_count / comment_count / play_count / admire_count` |

**入口链路也已跑通**：用户从抖音 App「分享名片」复制的短链 `v.douyin.com/xxxxx/`，一次 302 直接得到 `sec_uid`。这与得到大脑要求用户提供的正是同一样东西，佐证了两者走的是同一条路。

### 3.2 为什么初版判断错了

| 初版测试 | 结果 | 遗漏 |
|---|---|---|
| curl 裸请求 aweme/post | size=0 | 未意识到差异在于「有无 JS 运行时」而非「签名算法」 |
| `yt-dlp` 用户主页 | `Unsupported URL` | 这只说明 yt-dlp 未实现，不等于平台无入口 |
| `iesdouyin/share/user/` | JS challenge 壳 | 该入口确实死了，但它不是唯一入口 |

三条路都死于同一个原因——**它们都在浏览器之外**。而结论被错误地推广成了"平台无入口"。

### 3.3 Readboard 落地方案

Readboard 已 `import WebKit`（`ContentView.swift:2`、`Design/Styles.swift:5`），无需引入任何新依赖：

1. 创建**离屏 `WKWebView`**（不显示 UI），加载 `https://www.douyin.com/user/{sec_uid}`
2. 等待页面 JS 初始化完成（约 6–8 秒，或轮询探测）
3. 用 `evaluateJavaScript` 在页面上下文内 `fetch` 投稿接口，返回 JSON 字符串
4. Swift 侧 `JSONDecoder` 解析 → 映射为 `ParsedEntry` → 复用 `SourceStore.upsertContent`
5. `play_addr` 写入 `meta.audio_url` → 现有 `TranscribePipeline` 自动转写 → LLM 加工

**衔接点**：
- `guid` = `aweme_id`；增量游标 = `max_cursor`
- `identifier` = `sec_uid`；添加源时接受短链，自动 302 解析
- 在 `SourceStore.swift:82` 的 `transcribable` 判断中加入 `douyin`
- `desc` 作为标题与摘要，正文由转写产出，`fetch_status` 跳过 `FullTextFetcher`

### 3.4 待验证与风险

| 项 | 等级 | 说明 |
|---|---|---|
| **WKWebView(WebKit) 与 Chromium 的等价性** | **中·必测** | 本次实测在 Chromium 完成。抖音可能对 Safari/WebKit 有不同的指纹策略，需在 Swift 侧做一次真机验证后再排期 |
| 单次仅返回首页 16 条 | 低 | 翻页时第 2 页返回 0 条。对"每日增量"场景无影响——16 条足够覆盖单个博主一天的发布量。这也解释了得到大脑为何采用「每天 8 点、只取前一天」的低频设计 |
| 页面结构 / 接口参数变更 | 中 | 参数列表可能调整；但因不依赖签名算法，抗变更能力**远强于**逆向方案 |
| 请求频率风控 | 中 | 必须低频。建议每源每日 1 次、源间随机延迟、复用同一 WebView 上下文 |
| 资源开销 | 低 | 离屏 WebView 常驻内存约数十 MB，同步完毕即销毁 |
| 合规 | 中 | 公开内容、个人自用、非商用；不得绕过登录可见性限制。频率必须克制 |

### 3.5 建议

**值得排期，但优先级排在哔哩哔哩之后。** 理由：B站零认证入口的工程量更小、稳定性更高；抖音方案需先完成 WKWebView 等价性验证，且引入了"浏览器引擎参与后台同步"这一新的架构模式，应在 B站 打通信源管线后再引入。

## 四、小红书 — 技术路径成立（登录态 + 内置扫码），卡点在风险而非技术

> **2026-07-31 修订**：原判「不可行」不准确。实测证明卡点是**鉴权层**而非签名层，
> 且小红书官方提供扫码登录接口，可在应用内完成登录。技术路径完整闭合，
> 剩余的是**账号风险决策**，不是工程可行性问题。

### 4.1 实测结果（真实浏览器引擎，Chromium 131）

**签名层 — 已解决**

| 探测项 | 结果 |
|--------|------|
| `window._webmsxyw` | ✅ **`typeof === "function"`**，页面直接暴露签名函数 |
| `window.xhsFingerprintV3` | ✅ `object`，设备指纹模块同样暴露 |
| 调用 `_webmsxyw(path, body)` | ✅ 返回 `{X-s, X-t}`，可直接作为请求头 |

签名与抖音 a_bogus 同为 JS 混淆产物，但**同样不需要逆向**——页面自己把生成函数挂在 `window` 上。

**鉴权层 — 未登录时硬拦截**

| 探测项 | 结果 |
|--------|------|
| 页面自身发出的 `v2/user/me`、`v1/system/config` | ❌ `code=-101 无登录信息，或登录信息为空` |
| 手动 fetch `user_posted`（无签名头） | ❌ HTTP `406`，`{"code":-1}` |
| 带 `X-s/X-t` 调 `user_posted`（缺 `x-s-common`） | ❌ HTTP `461`，`data:{}` 空 |
| 导航到**博主主页** `/user/profile/{id}` | ❌ 正文仅 133 字，**强制弹出扫码登录墙**，`user_posted` 根本不发出 |
| 未登录**首页** `/explore` | ⚠️ 可渲染 29 条推荐笔记（但是算法推荐流，非订阅入口） |

关键对照：**博主主页在未登录时零 API 请求、零笔记卡片**，页面文案为「登录后推荐更懂你的笔记 / 扫码 / 手机号登录」。这与抖音「未登录即返回完整作品列表」形成本质区别。

**扫码登录 — 官方接口完整可用**

| 接口 | 结果 |
|------|------|
| `POST /api/sns/web/v1/login/qrcode/create` | ✅ `code=0`，返回 `qr_id` / `code` / `url` |
| `GET /api/sns/web/v1/login/qrcode/status?qr_id=&code=` | ✅ `code=0`��返回 `code_status` |

`code_status` 状态机：`0`=未扫描 → `1`=已扫描待确认 → `2`=已确认（下发登录态）→ `3`=已失效。
二维码内容即 `data.url`（形如 `https://www.xiaohongshu.com/mobile/login?qrId=...&xhs_code=...`），
渲染成二维码图片供用户用小红书 App 扫描即可。

**登录态持久化 — 条件具备**

| Cookie | domain | httpOnly | 过期 |
|--------|--------|----------|------|
| `web_session`（登录态凭据） | `.xiaohongshu.com` | **true** | **2027-07-31（约 1 年）** |
| `a1` / `webId`（设备指纹） | `.xiaohongshu.com` | false | 2027-07-31 |
| `gid` | `.xiaohongshu.com` | false | 2027-09-04 |

`web_session` 有效期约一年，且 `WKWebsiteDataStore` 能持久化 httpOnly Cookie，无需手工搬运。

### 4.2 判断

技术链路已完整闭合，且**比抖音方案更简单**——不需要手工拼签名头，只要 WebView 持有登录态，直接导航到博主主页，页面自身的 JS 就会发出带完整签名的 `user_posted` 请求，Swift 侧只需拦截响应。

真正的成本转移到了三处**非技术风险**：

1. **账号风险（主要顾虑）** — 需要用户的真实小红书账号长期登录在 Readboard 内。小红书对非官方客户端的风控在四个平台中最激进，异常调用频率可能触发限流甚至封号。用户主账号的社交资产远大于本功能收益。
2. **登录态维护** — `web_session` 名义有效期一年，但平台可能因异地/异常行为提前失效，需要设计过期检测与重新扫码引导。
3. **合规边界** — 已登录状态下的自动化采集，违反用户协议的程度高于未登录的公开数据抓取。

### 4.3 建议

**不列入默认排期，但从「不可行」改判为「用户可选的高级功能」。**

若要实现，应满足三个前置条件：
- 排在抖音之后——两者共用「离屏 WebView 采集器」基建，抖音无需登录态，是更好的验证载体。
- 明确的风险告知 UI：添加信源时必须提示账号风险，让用户知情后自行决定。
- 保守的同步策略：单博主每日 1 次，随机延迟，失败即退避——参照得到大脑「每天 8 点」的低频设计。

技术方案（供未来参考）：`WKWebView` + 持久化 `WKWebsiteDataStore` → 内嵌扫码登录页（或直接加载小红书登录页让用户扫码）→ 登录成功后导航博主主页 → `WKNavigationDelegate` / `URLSchemeHandler` 拦截 `user_posted` 响应 → 解析 `data.notes[]`（含 `note_id` / `display_title` / `type` / `interact_info`）→ `cursor` + `has_more` 做增量分页。

## 五、优先级建议

1. **哔哩哔哩** — 下一个实现。从**收藏夹信源**切入（零认证零签名，最小可用），再扩展到 UP 主动态（WBI 签名）。
2. **抖音** — 值得排期，但需先做 WKWebView 等价性验证（§3.4）。排在 B站 之后，因为它引入"浏览器引擎参与后台同步"这一新架构模式。
3. **知识星球** — 方案已完成至函数级（见 `~/.workbuddy/plans/radiant-forging-turing.md`），挂待办。
4. **小红书** — 技术可行但不列入默认排期。若做，必须排在抖音之后（复用同一套 WebView 采集器基建，且抖音无需登录态，是更安全的验证载体），并附账号风险告知。

### 两项共性基建

- **per-source 认证能力** — `content_source.config` 增加 `auth` 字段 + `FeedFetcher` 注入认证头 + `SecretStore` 存 token。B站（可选增强）与知识星球（必需）都依赖它。
- **离屏 WebView 采集器** — 抖音方案的核心基建。一旦建成，任何"需要浏览器环境才能取数"的平台都能复用同一套机制。这是比单个信源更有长期价值的能力。**小红书方案完全复用它**，只需额外增加「持久化登录态 + 内置扫码登录」两个能力，边际成本显著低于从零实现。

## 六、方法论教训

初版评估把「curl 测不通」等同于「平台无入口」，这是本次调研最大的失误。正确的提问方式是**分层的**：

1. 该平台是否存在返回增量列表的接口？（抖音：**有**；小红书：**有**，`user_posted`）
2. 该接口是否需要签名？（抖音：**是**；小红书：**是**）
3. 签名能否用纯代码复现？（两者皆：**否**）
4. **签名能否交给平台自己的 JS 生成？**（抖音：**能**；小红书：**能**，`window._webmsxyw`）
5. 该接口是否需要鉴权（登录）？（抖音：**否** → 直接可行；小红书：**是** → 进入第 6 步）
6. **登录态能否在应用内合法取得并持久化？**（小红书：**能**，官方扫码接口 + `web_session` 有效期约一年）
7. 取得登录态的**代价**是否可接受？（小红书：需用户主账号，**这是唯一真正的卡点**）

两次修正暴露了同一类错误的两种形态：

- **第一次（抖音）**：把「curl 测不通」等同于「平台无入口」。漏掉了第 4 步——宿主环境有浏览器引擎这个前提被默认为不存在。
- **第二次（小红书）**：把「需要登录」等同于「不可行」。漏掉了第 6 步——**平台自己提供了扫码登录接口**，登录态是可以在应用内正当取得的，不必假设用户要手工搬运 Cookie。

共同的教训：**不要在遇到第一个障碍时就停止提问。** 每个「不行」后面都应该追问一句「那有没有别的层面能解决它」。同时，把「技术不可行」和「代价不可接受」严格区分开——前者是死路，后者是可以交给用户决策的权衡。小红书属于后者，不该被写成前者。
